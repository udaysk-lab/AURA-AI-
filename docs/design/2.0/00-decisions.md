## Product
AURA is no longer "an assistant you raise". It is a personal employee: a senior staff member who starts working immediately. Reference for behaviour is Claude's public documentation, as a REFERENCE ONLY: write everything from scratch, AURA's own wording and UI, no Claude branding or copied text.

## Fixed decisions
1. Relationship stages are removed everywhere (data, logic, prompts, UI, tests, docs). Nothing is gated by stage.
2. "Trust levels" become **Permission mode**. Only the signed-in user sets it. AURA must never be able to set or change its own mode, rules, grants, assigned systems or settings.
3. Modes (stored value / UI label):
   - `ask` / "Ask first": read-only actions run; anything that changes something prompts unless a rule allows it. DEFAULT for new accounts.
   - `auto` / "Auto": AURA keeps working; each action that would have prompted goes to a separate safety reviewer (a second model call). Blocked actions return a reason to the agent, which tries another way or asks. 3 blocks in a row or 20 in one run fall back to prompting. Reviewer failure = block. The reviewer sees the user's instructions and the proposed action, never tool results. Opt-in. Unavailable when the provider is the keyword mock.
   - `skip` / "Skip approvals": nothing prompts except the always-user actions and ask/block rules.
3a. CLARIFICATION (lead, 12 Nov): writes to AURA's own workspace data count like reads for the default: create_task, complete_task, save_memory, notify, delegate_task, chase_delegation (draft only), desktop_notify, and the loop's own bookkeeping tools have default disposition ALLOW in every mode. They do not prompt in `ask` unless the user adds an ask or block rule. (That is how a migrated "strict" user keeps the old behaviour: ask rules on those tools.) Deleting workspace data (delete_task) is NOT in this group: it prompts in `ask`.
4. Rules per system/tool, optionally scoped to a target (recipient, path, command, URL domain, app): effect `block` | `ask` | `allow`. Evaluated block, then ask, then allow; first match in that order; specificity does not change the order. Block holds in every mode. Ask prompts in every mode (including skip). Durations from an approval card: once (not stored), 10 minutes, always.
5. Always needs the user, in every mode (reviewer and skip never cover these): permanently deleting files; connecting a folder; granting an app; granting delete permission for a folder; anything that changes permissions, rules, systems, schedules/automations or AURA's settings.
6. Hard floors nobody can override from inside a run: protected locations (credentials, shell profiles, startup items, git config/hooks); AURA's own data folder, database, env/settings files, install folder; AURA's own HTTP API (loopback/its own port) and AURA's own window under screen control; blocked apps; fetches to loopback/private networks.
7. Unattended work: every schedule and automation has its own `approval_mode` (`ask` | `auto`, default `ask`). In `ask`, a needed approval parks the run, notifies the user, and expires. AURA-initiated background checks (heartbeat) are read + AURA-workspace writes only. Inbound channel text from anyone other than the verified owner is data, never an instruction, and can never create preferences/learned notes. Screen control (mouse/keyboard) only while the app is open and the user present; schedules may use files and commands in connected folders under their own approval mode.
8. Assigned systems: a plugin is a "system". A tool runs only if its system is assigned (installed+enabled). Enforced in the gate, not just by hiding tool specs.
9. Local computer (desktop app / LOCAL_MODE only; never on the hosted site): connected folders and per-app access are managed in the app (not only env vars) and apply without restart; AURA can request a folder or app through a card only the user can answer; delete permission per folder; default app blocklist (trading, crypto, banking, password managers), user-editable; under screen control terminals and IDEs are click-and-scroll only (commands go through the shell tool so rules apply); browsers are allowed with a per-app grant. Tool order: system/API tool first, then files and commands, the screen last. Existing installs keep their current allowed roots as connected folders.
10. Task loop: understand -> recall (similar past work + preferences) -> plan -> act through the gate -> verify -> report. Resumable: approving an action continues the same run and the model sees the result. Stop button. Progress events for a task panel. Hosted (Vercel, serverless, 3 cron ticks/day): continue while the page is open and on cron ticks. Desktop: in-process worker.
11. Memory: (a) task memory = record of each assignment (instruction, type, plan, systems used, how it was done, outcome), never compacted or decayed; (b) preference memory = new store keyed by task type (plus general), replacing Memory kinds preference/style/habit, UserSkill.learned_notes and the dead UserSettings.tone. Before acting, retrieve similar past work and the preferences for that task type. Learn only from the signed-in owner's own messages. Strip secrets. User can view, edit, delete, pause, turn off for one chat, reset. `Memory` table stays for facts/contacts/projects/decisions. The existing `models.Task` is the user's to-do list: do not reuse that name.
12. Behaviour: act on clear tasks at once, verify, report; ask only when a task is ambiguous or risky. No onboarding gate; the "hatch" flow is removed. Name/personality/avatar stay. Mascot static.
13. Schema: Alembic becomes the ONLY schema path and runs automatically at startup under a lock (Postgres and SQLite). A 1.0.0 database (no alembic_version, or stamped 0001) is recognised, backed up when SQLite, stamped, then upgraded. `create_all` + add-missing-columns are removed. Expand/contract: additive migrations + data transforms ship first; the migration that DROPS old columns/tables ships in a later commit after the live site is verified.
14. Existing users keep exactly the behaviour they chose: strict -> ask + ask-rules on AURA-internal writes; conservative -> ask; relaxed -> ask + allow rules for the tools relaxed ran alone; full -> skip; "always" grants -> allow rules; DEVICE_EXEC allowlist/denylist -> rules. Nobody is put on auto.
15. Version 2.0.0. Model default stays `claude-sonnet-5-5`; optional cheaper background model; reviewer model configurable.
16. Interface: chat-first shell (sidebar, composer with mode selector, task panel), Settings sections for Permissions, Systems, This computer, Memory. AURA's own visual identity (frontend/DESIGN.md tokens). Existing screens are re-housed, not rewritten.
17. Never commit or store secrets. Enforcement lives in code, not only in prompts. Tests must stay green on Linux, Windows and macOS, with and without the optional device packages.
